## (d) NEW discrepancies found, beyond the 6 gaps already documented in tasks.md

None of these were on the pre-approved documented-gap list (a through f in the verification brief). All are WARNING severity: none breaks a spec invariant or a passing test; all are either cosmetic, already self-flagged in tasks.md as a recommendation to reconcile without being fixed, or genuinely new observations from this independent pass.

1. AGENTS.md line 204, a stale and contradictory bullet not caught by the T-PR14-004 grep gate. Under the DIAN section, line 204 reads "100% centralized in cloud admin", immediately followed on lines 205-206 by the correctly amended D1-rev text describing branch-local emission and numbering with no behavioural difference between online and offline. Line 204 was not one of proposal section 9.5 six explicitly quoted corrections, which targeted lines 112, 113, 205-207, 208, 234-235, and 255 of the pre-PR14 file, so T-PR14-003 never touched it, and T-PR14-004 repo-wide grep only checks for five literal banned terms (consecutivo_actual, numero_temporal, numero_oficial, sync_back_event, SyncBackEvent). "100% centralized in cloud admin" contains none of them, so it passes clean. Read literally, it contradicts the very next line branch-local numbering model. This is exactly the class of defect R21 exists to prevent, and it survived the R21 gate because the gate is a literal-term grep, not a semantic check. Recommend a follow-up edit that either deletes this bullet or rewords it to scope it to DIAN provider submission being centralized in cloud, which remains true post-D1-rev, rather than leaving it unqualified.
2. The sync_dependency_wait gauge label mismatch remains open. operations.md REQ-OPS-006 specifies labelnames tabla and uuid_sucursal; the shipped code and design.md section 9 both use tabla and tabla_padre instead. This was self-flagged in the T-PR13-001 status note as recommend reconciling operations.md but never resolved in either direction. Functionally the code choice is the semantically correct one for a waiting-on-which-parent gauge; this is a spec-text fix, not a code fix, but it remains an open, unresolved spec-code divergence at the end of PR14.
3. 0012_add_sync_queue_lw_buffer.py REVOKE scope diverges from REQ-CUT-010 literal text (see invariant 2 above); disclosed and justified in tasks.md, but the spec text itself was never amended to reflect the carve-out, so a future reader of cutover-migration.md alone would expect a blanket REVOKE UPDATE, DELETE that does not exist in the shipped migration.

Two runbook filenames do not match their alert rules: docs/runbooks/sync/dependency_wait.md and client_volume.md document FEProviderError and FENumberingExhausted respectively, not what their filenames suggest (DependencyWaitGrowing and ClientMasterVolumeHigh, both superseded names from design.md section 9 that operations.md REQ-OPS-008 replaced without a matching task updating the T-PR13-005 filename list). Self-flagged in the T-PR13-005 status note with a recommended rename, not yet done.

This is pure tasks.md documentation staleness, already explained by the PR5 own renumbering note that updating another PR section is that PR own responsibility, not a code defect. SUGGESTION severity only, worth a cheap follow-up edit before archive.
